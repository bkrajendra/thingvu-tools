## Phase 3 — KiCad 11 mutation path (headless first)

Exit criteria (plan §14): all Tier 1 headless acceptance criteria (plan §9). The two-resistor demo goes end to end through MCP tools.

- [x] **3.1 `OperationPlan`** (`kicad-domain/src/plan.rs`) — operations `place_symbol`, `add_wire`, `add_label`; expected nets as `REF.PIN` sets; references per component; findings. Plans are deterministic. Limit of 200 operations.
  - **Review:** plan §10 suggested at most 50 operations per plan. The label-per-pin layout needs more, so the limit is 200.
  - **Review — staleness:** KiCad's IPC exposes no document revision, so a plan records a fingerprint of the document (symbols with ids, references, values, positions, orientations, plus net topology). Any change to these makes the plan `STALE_PLAN`. Changes that touch neither (e.g. moving a label without changing connectivity, editing text) are not detected.
- [x] **3.2 Layout** — symbols on a grid (5 per row, cell size from the largest symbol's pin extent plus margin), below any existing symbols. A two-pin net on one horizontal or vertical line with no pin in between becomes a wire with one label; any other net gets a same-name local label on each pin. References: the preferred one if free, otherwise the library prefix plus the next free number. Pin geometry comes from KiCad's library before placement (`GetItemsFromLibrary`). Multi-unit symbols are refused (`MULTI_UNIT_UNSUPPORTED`).
  - **Review — readability:** labels sit directly on pin ends and crowd the reference/value text (see a `sch_render` of the demo). Connectivity is correct. A later layout pass should add short wire stubs leading away from each pin, with the label at the stub end (needs the pin direction from the library).
- [x] **3.3 `sch_plan_changes`** — takes a `CircuitSpec` JSON; nothing is changed. Returns `plan_id`, `can_apply`, counts, references, operations in mm, expected nets, and findings.
- [x] **3.4 `sch_apply_plan`** — needs `confirm: true` and an `idempotency_key` (8–128 characters). Repeating a key replays the earlier result; reusing an applied plan, or a plan whose fingerprint no longer matches, gives `STALE_PLAN`. Applies in **two commits** (placement, then values/wires/labels): inside an open commit a newly placed symbol is not yet in the document, so it cannot be updated (finding below). A failed step's commit is dropped and earlier steps' items are deleted, giving `rejected` with `mutation_state: not_applied` (tested). Afterwards connectivity is read back and compared pin-for-pin with the expected nets; a mismatch gives `result_state: partial`.
  - **Finding:** headless sessions *do* support commits when the document is opened with `OpenDocument`/`CreateDocument`. Phase 0 tested a server started with a file argument, which does not. Compatibility record corrected.
  - **Review — undo granularity:** one apply is **two** undo steps in the GUI, not one as the plan intended. Merging them needs either a placement call that sets field values, or KiCad exposing staged items to `UpdateItems`.
  - **Review — key reuse after failure:** a failed apply that changed nothing (refused before any request) can be retried with the same key. A failed apply after KiCad was contacted marks the plan and key as used, so the caller must make a new plan.
- [x] **3.5 Field updates** — `UpdateItems` without the embedded `definition`, with a field mask (`value_field`, plus `footprint_field` when set). Each value is read back after updating; headless, no duplicate library symbol appears.
  - Verified in the GUI on 24 Oct 2026 (task 4.7): values persist with the masked update.
- [x] **3.6 Transforms** — placement sets rotation through `PlaceSymbolFromLibrary` (0° is sent as "unset"), and position and reference are read back after placing. The layout uses rotation 0 only, so writing other rotations and mirrors is not exercised yet. Follow-up when the layout starts rotating symbols: read back every written transform (see 2.5). **Status (v0.3.0):** the tidy, `sch_arrange_plan`, and the hints now rotate and mirror symbols, and the live tests apply them (nets verified, ERC clean), but the apply step does not yet compare each part's position and transform with what the plan asked for; it only checks nets. **Closed in Phase 9 (9.2):** the apply step now reads every placed, moved, or changed part back and compares it with the plan.
- [x] **3.7 Save, ERC, export, render** — `sch_save` (`SaveDocument`); `sch_run_erc`, `sch_export_netlist` (to a `.net` inside the schematic's folder), and `sch_render` (PNG returned as an MCP image, 72–600 dpi) all run `kicad-cli` on a `SaveCopyOfDocument` snapshot in a private folder, which is deleted afterwards.
  - **Finding:** KiCad's IPC export jobs read the saved file, not the in-memory document. A never-saved document fails "Failed to load schematic", and a saved one would silently ignore unsaved changes. Hence the snapshot approach.
  - **Review:** `sch_render` returns the first page only; multi-sheet designs are out of MVP scope.
  - **Review — read-only mode:** `--read-only` refuses `sch_apply_plan`, `sch_save`, `sch_export_netlist`, and the apply step of `sch_create_demo_circuit`. Planning, reads, ERC, and rendering stay allowed; the latter two only write to private scratch folders.
- [x] **3.8 `sch_create_demo_circuit`** — plans the bundled two-resistor spec, and applies it with `apply`, `confirm`, and `idempotency_key`.

Tests: `kicad-domain` 20 unit tests (layout, references, unknown pins, wire rule); `kicad-session/tests/live_mutate.rs` (plan → apply → verify → save → kicad-cli; stale plan; cleanup after a failed placement); `kicad-ai-mcp/tests/stdio.rs` (whole demo through the MCP binary, including idempotent replay, stale plan, ERC, render image, export path rule, save, independent kicad-cli check; read-only mode). All pass offline and live.

Phase 3 exit check: met for headless. The demo is planned, applied, verified, saved, and checked independently through MCP tools on the nightly. The GUI counterpart is Phase 4.

## Phase 4 — KiCad 11 GUI provider (plugin)

Exit criteria (plan §14): all Tier 1 acceptance criteria. The demo works live in the Schematic Editor, with undo.

- [x] **4.1 `kicad-ai-plugin`** (`crates/kicad-ai-plugin`) — executable plugin with `register` (default), `unregister`, `list`. `register` reads `KICAD_API_SOCKET` and `KICAD_API_TOKEN`, confirms the instance answers with that token pinned, records it, prints one status line (shown in KiCad's message area), and exits.
  - **Review — registrar instead of bridge:** the plan described a long-running bridge process that relays requests over its own local protocol (`kicad-ai-bridge/v1`). KiCad's API accepts any local client, and the token only pins the instance. So the plugin is a registrar: the MCP server connects to the registered KiCad itself, with the token pinned. No relay protocol, no plugin process to keep alive or orphan; the plugin-lifetime question from 0.11 no longer applies. Plan §1, §3.1, and §6 are updated to match.
  - **Review — token storage:** the instance token is written to `%LOCALAPPDATA%\thingsvu\kicad-ai\instances\<hash>.json` (user-only folder by default). It is never shown in tool results or logs; `session_status` lists only version and projects. It is an instance identifier, not an access secret (KiCad accepts tokenless local clients).
- [x] **4.2 Registry** (`kicad-session::registry`) — one JSON record per KiCad endpoint (FNV hash of the socket path), atomic writes, newest first. Unreachable or token-mismatched records are removed when `session_status` or `session_open` looks at them. `THINGSVU_REGISTRY_DIR` overrides the folder for tests.
- [x] **4.3 GUI session provider** — `Session::open_gui`: connects with the token pinned, picks the root schematic by `schematic_path` or the only open one, probes capabilities in GUI mode, and pairs the session with the `kicad-cli` of the same KiCad series. Closing only disconnects: the editor, document, and unsaved changes stay with the user. Provenance reports `provider: gui`.
- [x] **4.4 MCP** — `session_open` takes `provider: "gui"` (schematic path optional); `session_status` lists `gui_editors` (version and projects).
- [x] **4.5 Packaging** — `plugin-package/plugin.json` (schema-valid for the 10.99 build: `exec` runtime, `schematic` and `pcb` scopes), toolbar icons (light/dark, 24/48 px), `scripts/install-plugin.ps1` (resolves the real Documents folder, e.g. OneDrive; refuses KiCad < 10.99), and `scripts/uninstall-plugin.ps1`. Installed into the nightly's plugin folder on the development machine.
- [x] **4.6 Automated test of the plugin path** — `kicad-ai-plugin/tests/live_plugin.rs`: a headless KiCad stands in for the editor (it has a socket and a token, as KiCad gives a plugin). Covers the real plugin binary registering and unregistering; the GUI provider opening by path and by default; refusal of an unopened path and of a wrong token; closing without stopping KiCad; and the explanatory message when run outside KiCad.
- [x] **4.7 Live GUI check** — run on 24 Oct 2026 against the nightly Schematic Editor (`gui_editor_demo`, `THINGSVU_GUI=1`), project `D:projectskicad-demo` (saving approved by the project owner):
  - The toolbar button registered the editor; `session_status` listed it; `session_open` with `provider: gui` found `kicad-demo.kicad_sch` on its own.
  - The demo applied live and was verified pin for pin; `undo_steps: 2`.

  - **`sch_save` works in the GUI** (`SaveDocument`). The saved file, checked with `kicad-cli`: nets `/INPUT`=R1.1, `/MID`=R1.2+R2.1, `/OUTPUT`=R2.2; values `10k`; one library symbol.

## Phase 5 — Readable schematics (layout engine)

Motivation: the project owner's test (24 Oct 2026). Claude built a 3.3 V regulator with the Phase 3 tools. It was electrically correct, but read as a grid of parts joined only by net labels, with power drawn as text labels and text overlapping. Phase order changed (option A): readable schematics now comes before the KiCad 10 fallback (Phase 6) and hardening (Phase 7).

Exit criteria: golden circuits (3.3 V regulator first) laid out with signal flow, power symbols, and wires, passing automated readability checks and a rendered review; netlist verification unchanged.

- [x] **5.1 Golden circuits** — `docs/examples/regulator-3v3.json` (the owner's regulator: connector, fuse, Schottky, AMS1117, decoupling, power LED, flags) and `docs/examples/ne555-blinker.json` (an IC with parts on several sides). Both are planned and checked offline, and built, verified, and rendered live by `crates/kicad-session/tests/live_layout.rs` (`KICAD_LIVE=1`; renders go to `THINGSVU_LAYOUT_OUT`).
  - **Review:** an LED driver and an MCU-with-decoupling circuit are not added yet; the NE555 covers the "IC with parts around it" case for now.
- [x] **5.2 Richer library geometry** — `LibrarySymbol` gains `is_power` and a body box (from the symbol's graphics); `LibraryPin` gains `outward` and `electrical_type`. `power_symbol` finds `power:<net>` (and `power:GND` for ground names); `library_ids_for` lists every symbol a spec needs, power symbols included.
- [x] **5.3 Net and part roles** — nets are ground, power (a matching power symbol exists), or signal. Parts are main (on the signal path), shunt (one pin to ground, one to a main net), or attached (power-library parts such as `PWR_FLAG`). Connectors are never shunts.
- [x] **5.4 Placement by signal flow** — columns by breadth-first distance from the source connector; the main path on one baseline, left to right; shunts below their net at a fixed pitch. Orientation is chosen by cost (pins facing their neighbours, ground facing down); connectors and multi-pin parts may also be mirrored. Parts with 4 or more non-ground pins are laid out as a **hub**: the IC keeps its drawing with a stub and a name on every pin, and the other parts form blocks (joined by nets the IC does not touch), each drawn as a chain — connector blocks to the left, the rest to the right in wrapping rows.
  - **Review — hub layout:** blocks connect to the IC through same-name labels, not wires (the usual style for an IC with many pins). Wiring short block-to-IC connections directly is a possible later refinement.
  - **Review:** the hub threshold (4 connected non-ground pins) is a heuristic.
- [x] **5.5 Power symbols and stubs** — power and ground nets are drawn as power symbols. A rail on the baseline is named once, at its longest gap; ground pins get a stub or an L-shaped run and a ground symbol facing down. Supply symbols on side pins stand upright on a longer stub. Every candidate shape must stay clear of other nets (`touches_other_net`), and a ground symbol must also clear every part body (an LED's arrows reach past its pin end, so the LED gets a stub).
- [x] **5.6 Wires** — the baseline rail with drops to shunts, junctions where three or more connections meet, and stub-plus-label (or power symbol) as the fallback when a net cannot be wired. Flags (`PWR_FLAG`) go on a point of their net, choosing a position and direction whose body stays clear of wires, parts, and power symbols, with one grid of room for text when it fits.
  - **Attention:** routing is the rail-and-drop pattern plus fallbacks, not a general maze router. Nets that do not fit it become labels (reported as `fallback_nets`); none of the golden circuits needs one.
- [x] **5.7 Apply support** — new operations `place_power_symbol`, `add_label` (with direction), and `add_junction`, plus mirrored placement (set through a masked `transform` update in the second commit). Placement, mirror, and value are read back and compared by effect (`Orientation::same_effect`, since KiCad normalizes transforms). Power symbols get `#PWR`/`#FLG` references, which verification ignores.
  - **Review:** the mapping from label direction to KiCad's spin style is set by reasoning and looks right in renders, but has not been checked label by label against the GUI.
- [x] **5.8 Readability checks** — `kicad-domain::readability` checks a plan's geometry independently of the layout: shorts between nets (error `LAYOUT_SHORT`), overlapping symbol bodies and wires through bodies (warnings `SYMBOLS_OVERLAP`, `WIRE_THROUGH_SYMBOL`), and power nets drawn as labels. The report is in the `sch_plan_circuit` result (`readability`). Unit tests require both golden circuits to be clean against the test library, and the live harness requires the same against KiCad's real libraries.
  - **Review:** a wire that leaves a symbol's own pin is not counted as passing through it, because some graphics (LED arrows) overhang the pin end.
  - **Attention:** field text (reference, value, and flag text) is not measured, only kept clear by spacing. Next to a two-pin connector the `PWR_FLAG` text can still crowd nearby wires (visible beside J1 in both renders).
- [x] **5.9 Layout hints and editing tools** — done in Phase 8 (v0.3.0): `sch_describe_layout`, `sch_arrange_plan` (move, turn, mirror, delete), `sch_reconnect_plan`, layout hints on `sch_tidy_plan`, and `sch_set_field` (see 8.1–8.6).
  - **Review:** optional layout hints and `sch_move_symbol` / `sch_rotate_symbol` / `sch_add_wire` / `sch_delete_items` are not done. Proposal: do them early in Phase 7, or as their own small phase if you want them before the KiCad 10 fallback.

## Phase 8 — Review and tidy existing schematics

Motivation (25 Oct 2026): the project owner asked an assistant to make the schematic open in the KiCad editor neat and readable. The tools could only add parts, so the assistant started editing the file on its own. This phase gives it a safe way to do that.

Exit criteria: an assistant can read a whole existing sheet, say what is untidy, plan a cleaner layout, and apply it with the same guarantees as for a new circuit — every net identical afterwards, nothing changed before the user confirms — on the live editor, on a headless session, and on a file.

- [x] **8.1 Read the whole sheet** — `SchematicDesign` (parts, wires, labels, junctions, text notes, and a count of items tidying cannot handle) read the same way from a live KiCad (`GetItems` for every item kind) and from a file (`kicad-sexpr`). Net-naming power symbols and flags that `kicad-cli`'s netlister leaves out are attached to their nets from the drawing, so file and API sessions report the same netlist.
- [x] **8.2 `sch_review`** — read-only. Reports counts, overlapping symbols and wires through parts (the same geometric checks used for new layouts), whether a tidy is possible and why not, and how much it would change.
- [x] **8.3 `sch_tidy_plan` and apply** — the circuit is read back from the design (parts and KiCad's nets), laid out again by the engine that lays out new circuits, and the difference becomes a plan: **move** each part, **remove** the old wires, labels, junctions, and net-naming power symbols, **add** the new drawing. Parts keep their identity, values, footprints, and fields. The existing `sch_apply_plan` applies it:
  - *file:* one verified copy, then atomic replace, as before; a part's text moves with it, in place, touching only the numbers that change;
  - *headless:* two commits, and a failed tidy reloads the saved file (so it refuses to start with unsaved changes);
  - *editor:* two commits (two undo steps); if something fails after the first, the error says how many times to press Ctrl+Z.
  Applying must leave **exactly the same nets**; ERC must not get worse (a live test asserts both on both backends). Tidying a tidy schematic changes nothing (`NOTHING_TO_CHANGE`).
  - **Decision:** the plan includes `moves` and `removals` next to `operations`, so one plan store, one apply tool, and one confirmation flow serve both new circuits and tidies.
- [x] **8.4 `sch_set_field`** — change one part's value or footprint, nothing else. One undo step in an editor; a file change must load in `kicad-cli` before it replaces the file.
- [x] **8.5 Manual editing: move, rotate, delete, and reconnect** (v0.3.0, added after the first live use) — sub-plan:
  - [x] **8.5.1 `sch_describe_layout`** — read-only: every part's reference, value, position (mm), rotation, mirroring, body rectangle, and each pin's position, facing, and net, plus the text notes' areas. What an assistant needs to decide where things go.
  - [x] **8.5.2 `sch_arrange_plan`** — bare edits of named parts: move (`x_mm`/`y_mm` or `dx_mm`/`dy_mm`), turn (`rotate_deg`, counter-clockwise from now), mirror, and delete. Only those parts change; **wires stay and break** (the plan counts the wires left behind and warns about new overlaps). Goes through the same plan, confirm, and apply flow as everything else (`moves`, and `removals` of kind `symbol`).
  - [x] **8.5.3 `sch_reconnect_plan`** — with every part where it is, remove all old wires, labels, junctions, and net-naming power symbols and draw the connections again, from the circuit **as it was before the first arrange** (the server remembers KiCad's netlist from just before it; `use_current_nets: true` uses what KiCad reads now). No part moves. Applying verifies the nets against KiCad as for any plan.
  - [x] **8.5.4 The router** (`kicad-domain::reconnect`) — each pin gets a stub; ground and power nets end in power symbols; other nets are a tree of straight, L- and Z-shaped wires that touch no other net and cross no part, with junctions where three meet; a net it cannot wire that way is named with a label at each pin and reported (`NET_DRAWN_WITH_LABELS`). Wired nets are named with a label unless KiCad's own name (`Net-(…)`) is enough.
  - [x] **8.5.5 Live, headless, and file** — one flow on all three providers (tested on file and headless; the GUI test is below). A reconnect may start from unsaved work on a headless session; if it fails, the saved file comes back.
- [x] **8.6 Layout hints** (v0.3.0) — `sch_tidy_plan` takes `keep` (parts that stay exactly where they are), `place` (a part to x_mm, y_mm, optionally turned or mirrored), and `near` (a part next to another, on a side, with a gap). With hints the parts are placed as asked (the rest as the layout engine would place them, nudged off the hand-placed ones) and the router draws the wires; an unknown part is a refused plan.
- [x] **8.7 Text-aware layout** — done in Phase 9 as 9.1.

Review of 8.5/8.6 (please look at these):
- **The moves leave a broken circuit on purpose**, as asked: the assistant places everything, then reconnects once. On a big circuit the router's wires will be less tidy than the layout engine's; for a whole sheet prefer `sch_tidy_plan`.
- **The remembered circuit lives in the server's memory.** If the server restarts between the arrange and the reconnect, KiCad reports the broken circuit and the reconnect would draw *that*. Reconnect right after arranging; the plan's `RECONNECT_NETS_FROM` finding says which circuit it used.
- **Deleting a part** keeps its wires until the reconnect; the nets that remain are drawn without it (`R2.2` alone on a net stays a stub).
- **Mirroring and turning are by effect**, so a mirrored part turns the way it looks on screen, and KiCad's normalised forms compare equal.
- Flags (`PWR_FLAG`) are wired by the router to the nearest pin of their net, or get a symbol of their own.
- **Not built:** moving a *group* as one unit, aligning or distributing parts, and moving wires, labels, or text notes by hand.

Things the tidy deliberately does or does not do (please review):
- **Refuses** sheets with buses, bus entries, global or hierarchical labels, directive labels, sheets, groups, tables, rule areas, or no-connect flags, and unannotated references. It says which, and changes nothing. Only flat, single-sheet designs.
- **Text notes and graphics stay where they are.** If the new layout would land on a note it is placed lower, below it (`TIDY_PLACED_BELOW_NOTES`). Other graphics (lines, boxes, images) are not avoided.
- **Labels stay labels.** A net the design names with a label (e.g. `VBUS`) keeps a label; a power symbol there would be a power input nothing drives, and ERC would start to complain. Nets that already have a power symbol get one again.
- **Unnamed nets** (`Net-(R1-Pad2)`) get no label when they are fully wired.
- **Power symbols are replaced**, not moved: their references are renumbered unless a symbol would be drawn exactly where it already is.
- The layout is the Phase 5 engine's: one row, with shunts below and hub layout for ICs. A design that was carefully hand-arranged will be rearranged to that style.
- Wires are compared as runs along a line, because KiCad joins wires that meet end to end.

Findings during the work (kept for the record):
- **Through the API a moved symbol's text stays behind.** The API moves the symbol and leaves its reference and value where they were, so the live path moves each field itself, keeping its place relative to the symbol. The text angle is stored relative to the symbol (as in the file) and is left alone.
- **`kicad-cli`'s netlist omits power symbols and flags** — see docs/kicad-api-compatibility.md. A flag joined to its net only through a ground symbol's name needed the name-based attachment.
- **Flags need `#`-prefixed references to validate** (`#FLG01`); the reference check now allows a leading `#`.

- [x] **14.6 Checkpoints** (#26) — `checkpoint_create`, `checkpoint_list`, `checkpoint_diff`, and `checkpoint_restore`.
  - They cover the project's `.kicad_pcb`, `.kicad_sch`, and `.kicad_pro`, kept in `.thingsvu/checkpoints/` in the project.

  - **Review:** (1) Four tools, each given a `session_id` (board or schematic) or a `project_path` (no session needed): `checkpoint_create` (`label`), `checkpoint_list`, `checkpoint_diff` (`checkpoint` or `latest`, `against` another id or `current`), `checkpoint_restore` (`confirm`). A checkpoint is a folder `.thingsvu/checkpoints/<UTC date-time>/` with copies of the root `.kicad_pcb`, `.kicad_sch`, `.kicad_pro` and a `manifest.json` (label, time, file sizes, an FNV-1a hash per file, KiCad version, whether unsaved changes are in it). A damaged copy is refused at restore. Sub-sheets and library tables are not kept. (2) A live session's open board and schematic are written into the checkpoint (`SaveCopyOfDocument`), so it holds unsaved changes too and says so; the same goes for `against: current`. (3) The diff is semantic, from `kicad_domain::changes`: footprints added, removed, or moved; tracks, vias, zones, and drawings; nets added or removed and tracks per net; schematic parts, wires, and labels; and the design rules (classes, assignments, patterns, minimums). When files differ but none of that does, it says so. (4) Restore: refused while a session has unsaved changes (it says how to save or drop them), for a gui session or a lock file that is not one of our headless servers', and in read-only mode. (6) The live test routes a board, saves, takes a checkpoint, rips everything up with `checkpoint`, sees the diff (`3 tracks removed`, three nets with 0 tracks), is refused over the unsaved rip-up, saves, restores, finds the tracks and the rules back in the open session, then undoes the restore. (7) Not done: restoring into an open editor (refused; close it there), the sub-sheets, and removing old checkpoints (they are plain folders; `.thingsvu/` belongs in `.gitignore` if the project is under version control).
- [x] **14.7 Schematic gaps** —
  - Circuit plans take `no_connects` (pins) and power flags on a named net, placed at that net (#7, #8).
  - `sch_pin_net_plan` moves one pin to another net, or swaps two pins' nets, redrawing only those pins' wires and labels (#9).
  - `sym_search` / `sym_get` find symbols by name, keyword, or description, and return a symbol's pins, units, default footprint, and footprint filters without placing it (#12).
  - **Review:** (1) **Circuit plans:** `no_connects: [{component_id, pin_number}]` and `power_flags: [net]` (`CircuitSpec`). A no-connect pin must exist and must not be in a net (`NO_CONNECT_PIN_IN_NET`); a flag net must be a net of the circuit (`POWER_FLAG_UNKNOWN_NET`). A power flag is written out as a `power:PWR_FLAG` part with its pin in that net (not counted against the 150 parts; one already on the net is not doubled), so the layout places it as before. No-connect flags are `Operation::AddNoConnect` at the pin's place; both providers write them and the apply read-back checks each is there. (2) **A bug found on the way:** a flag sits on the wire between a pin and the net's power symbol, and KiCad 10 does not connect a pin to the middle of a wire without a junction, so ERC on a KiCad 10 file session reported every flag unconnected and its supply undriven (the sheet the 13b/14 tests built, the regulator example included, had this). `drawing_operations` now puts a junction wherever a pin or wire end lands inside another wire; ERC of the two-resistor test circuit is empty on both providers. (3) **`sch_pin_net_plan`:** `move: {pin, to_net}` or `swap: [pin, pin]`. Where the drawing at the pin is a stub (a wire from the pin to a free end, or a wire that runs on into other wires), the pin's own wire and the label or power symbol at its end go and a stub with the new net's power symbol (or a label) is drawn: moving C5.1 from +3V3 to +5V on the regulator example is 1 removal and 2 additions, and the saved file has the same number of wires before and after. Where the pin sits in the middle of other wires, the wiring of the nets involved is worked out again as `sch_reconnect_plan` does and only their items are kept. A net whose only name went with the pin is named again by a label at one of its pins. The result is checked for new shorts and wires through parts before it is offered, and KiCad's netlist verifies every net on apply (both providers, live). A change that removes drawing items needs a saved document on a headless session, like a tidy. (4) **`sym_search` / `sym_get`:** the install's `share/kicad/symbols` and the project's `sym-lib-table` (as for footprints; the global table is not read). Search reads each library file once, line by line, in up to 8 threads, and keeps name, description, keywords, default footprint and its filters, datasheet, units, and pins (a derived symbol has its parent's) for the life of the process: the first search of the 224 stock libraries (235 MB) took 2 s in a debug build with warm file caches, later ones 50 to 100 ms. Results rank an exact name, a name that starts with the words, names, keywords, then descriptions. `sym_get` parses the one library properly and lists every pin (number, name, electrical type, unit, place, direction). (5) Not done: multi-unit symbols in circuit plans (refused as before), pin swaps between the units of one part, and the global symbol table.
- [x] **14.8 Autoroute control** (moved from 15.7; W6: Freerouting does the complex routing, nothing new is built) —
  - `nets` (route only these) and `exclude_nets`.
  - `keep_existing: true` treats tracks already drawn (hand-routed critical nets) as fixed, and routes only what is left.
  - Per-net widths through net classes in the DSN (#19), with the minimum width of 14.1.
  - The time limit always ends the whole process tree, and the hang is reported (#22).

  - **Review:** (1) Probes first (`live_probe14_dsn`): KiCad writes every track and via already on the board into the DSN as `(type protect)`, whether locked or not, and Freerouting keeps a protected wire as it is **and writes it again in its session**; so what the earlier phases called "the import replaces your tracks" was a delete and re-create of the same geometry (new ids, and a locked track would have been doubled if the session were imported over it, which the live test now checks does not happen). A net given no pins in `(network …)` is left alone: its pads become obstacles and its tracks stay. (2) `pcb_autoroute_plan` takes `nets`, `exclude_nets`, and `keep_existing` (default true, the old behaviour). The DSN is edited as text (`kicad_sexpr::dsn`): nets that are not routed lose their pins; with `keep_existing: false` the unlocked tracks and vias of the routed nets are taken out of the wiring (locked ones are matched by place and stay), so the router starts those nets from nothing. The plan reports `routes` (the nets routed, the nets left alone, `ripped_up` tracks and vias) and `replaces` computed from the session itself: `tracks` and `vias` are the ones that really change, `unlocked_tracks_identical` are the ones written again as they are. (3) **Per-net widths** needed no code: KiCad's DSN export writes the net classes (width, clearance, via) and Freerouting uses them; after `pcb_rules_plan` put GND in a 0.5 mm class, the session's narrowest GND track is 0.5 mm. The widening to the board minimum from 14.1 stays as the safety net. (4) **The time limit** now ends the whole process tree: `taskkill /T /F` on Windows, a process group kill elsewhere, done while the child still exists so the tree can be found. Before, only the program itself was killed (`kill_on_drop`): the test starts a helper from a program that hangs, and without the fix the helper is still running afterwards (checked by taking the fix out). The error says the router and everything it started were ended and nothing was routed. This is in the shared `kicad-cli` runner, so every `kicad-cli` call gets it. (5) Not done: routing with a Freerouting setting beyond passes and time limit (by design); fixing which layer a net uses; and the router's violation count rises when many nets are left alone (6 in the probe with four nets left bare), because their pads are obstacles without a net; DRC after the apply is the judge.
